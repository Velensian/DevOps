1.  <span style="--tn-background:#e64d4d;background-color:#e64d4d;">DNS</span> - служба, которая по имени возвращает ip адрес необходимого сайта. Распределенная телефонная книга
    1.  DNS распределенный, потому что не у всех хранятся адреса ко всем сайтам. Кто-то хранит какие-то адреса и с помощь каких-то частей поможет найти адрес. ИМЕНА ЧИТАЮТСЯ СПРАВА НА ЛЕВО. От общего к частному.
        
        docs.github.com.  
                                    └─ корень (точка в конце обычно не пишется)  
                            └──── зона .com  
                └─────────── домен github.com  
        └──────────────── поддомен docs
    2.  | Уровень | Кто хранит | Что знает |
        | --- | --- | --- |
        | корень `.` | 13 групп корневых серверов | кто отвечает за `.com`, `.ru`, `.org`... |
        | зона `.com` | серверы реестра `.com` | кто отвечает за `github.com` |
        | `github.com` | DNS-серверы самого GitHub | точный адрес `github.com`, `docs.github.com` и т. д. |
        
        браузер ──▶ «какой адрес у github.com?»  
          │  
          ▼  
        1\. локальный кэш на ноутбуке ─ уже спрашивали недавно? ── да ──▶ сразу ответ  
          │ нет  
          ▼  
        2\. DNS-сервер провайдера или роутера (резолвер)  
          │ не знает → идёт по цепочке:  
          ├──▶ корень:        «за .com отвечают вот эти серверы»  
          ├──▶ сервер .com:   «за github.com отвечают вот эти серверы»  
          └──▶ сервер GitHub: «github.com = 140.82.121.4»  
          │  
          ▼  
        ответ возвращается браузеру и запоминается в кэше  
          │  
          ▼  
        браузер подключается к 140.82.121.4:443
    3.  Резолвер(resolve - разрешить, найти) или же по другому DNS  сервер провайдера или роутера - это сервер который и ищет ip адрес нужного сайта из пункта b.
    4.  <span style="--tn-background:#e64d4d;background-color:#e64d4d;">Кэш и TTL</span> - Доставать DNS адреса по такой цепочке долго и не удобно, поэтому ip адреса приходят с TTL(Time To Live), с временем хранения адреса в кэше, например 1 час, через час опять придется бегать по серверам и искать адрес.
    5.  ### Типы записей
        
        В «книге» хранятся не только адреса. Главные типы:
    6.  | Запись | Что хранит | Пример |
        | --- | --- | --- |
        | `A` | имя → IPv4-адрес | `github.com → 140.82.121.4` |
        | `AAAA` | имя → IPv6-адрес |  |
        | `CNAME` | имя → **другое имя** (псевдоним) | `www.example.com → example.com` |
        | `MX` | куда доставлять почту домена |  |
        
        ### Файл `/etc/hosts`
        
        До всякого DNS система смотрит в локальный файл `/etc/hosts`. Там можно вручную прописать «имя → адрес». Именно там записано, что `localhost` это `127.0.0.1`. Его используют для тестов: «пусть `mysite.test` ведёт на мой ноутбук».
        
        ### Почему это важно для DevOps
        
        Половина фраз «сайт не работает» на деле оказываются «не работает DNS»: запись не создана, указывает на старый сервер, не истёк кэш. Поэтому при диагностике первый вопрос: **по имени не открывается, а по IP открывается?** Если так, проблема в DNS.
    7.  ### <span style="--tn-background:#e64d4d;background-color:#e64d4d;">Команды для DNS</span>
        
        Сначала описание, практика потом.
    8.  | Команда | Что делает | Пример |
        | --- | --- | --- |
        | `dig имя` | подробно спрашивает DNS и показывает ответ: записи, TTL, какой сервер ответил | `dig github.com` |
        | `dig +short имя` | то же, но выводит **только адрес** | `dig +short github.com` → `140.82.121.4` |
        | `dig имя @сервер` | спросить **конкретный** DNS-сервер, а не системный | `dig +short github.com @8.8.8.8` |
        | `resolvectl status` | показывает, к каким DNS-серверам обращается твой `systemd-resolved` |  |
        | `cat /etc/hosts` | показать локальный файл «имя → адрес» |  |
        | `ping имя` | проверить, отвечает ли машина: сначала узнаёт IP через DNS, потом шлёт пакеты. Выход `Ctrl+C` | `ping -c 3 github.com` (`-c 3` значит 3 пакета) |

2.  <span style="--tn-background:#e64d4d;background-color:#e64d4d;">HTTP</span>(Hyper Text Transfer Protocol)- протокол(правила) по которым клиент(например брузер) и веб-сервер обмениваются данными. HTTPS - тоже самое, но зашифрованное.
    1.  Коды ошибок - напрмер при попытке зайти на сайт вылезает ошбика 4хх - это ошибка клиента(например браузера), запросил что-то не то.(При этом эта ошибка будет только при удачной связи с DNS, если связи с днс нет, и кода ошибки не будет) https://github.com/Velensian/нет\_такого     → 404, сайт есть, страницы по этому пути нет
    2.  А если выпадает ошибка 5хх - это ошибка веб-сервера, запрос нормальный, но сервер не смог его обработать.
    3.  Путь после имени сайт показывает какую страницу ищем, на сайте.
    4.  <span style="--tn-background:#e64d4d;background-color:#e64d4d;">Главные коды ошибок HTTP</span>
    5.  | Код | Значение | Чья ошибка |
        | --- | --- | --- |
        | **200** OK | всё хорошо, вот ответ |  |
        | **301 / 302** | страница переехала, иди по новому адресу (перенаправление) |  |
        | **400** Bad Request | запрос составлен неправильно | клиент |
        | **401** Unauthorized | нужно войти (логин, токен) | клиент |
        | **403** Forbidden | вошёл, но прав нет. Ты видел это при `git push` с токеном без прав | клиент |
        | **404** Not Found | по этому пути ничего нет | клиент |
        | **500** Internal Server Error | в программе сервера ошибка (например, упал код на Python) | сервер |
        | **502** Bad Gateway | промежуточный сервер (например, nginx) не получил ответ от приложения за ним | сервер |
        | **503** Service Unavailable | сервер перегружен или на обслуживании | сервер |
    6.  <span style="--tn-background:#e64d4d;background-color:#e64d4d;">curl - HTTP клиент в терминале</span>
        1.  curl - программа, отправляющая HTTP запросы из терминала
        2.  | Команда | Что делает |
            | --- | --- |
            | `curl адрес` | отправить запрос и вывести содержимое ответа (HTML, данные) |
            | `curl -I адрес` | показать только **заголовки** ответа, включая код состояния, без содержимого |
            | `curl -s -o /dev/null -w "%{http_code}\n" адрес` | вывести **только код** (удобно в скриптах). `-s` без лишнего вывода, `-o /dev/null` выбросить содержимое, `-w` что напечатать в конце |

            во втором случае HTTP1 - 200, значит удалось подключится к самому гизабу, а дальше HTTP2 - 404, следовательно страница не найдена на сайте гитхаба
            
            По факту: 
            
            Коды прочитаны верно: у твоего репозитория **200**, у несуществующего пути **404**. Сайт GitHub один и тот же, разница только в странице. Ровно то, что мы разбирали.
            
            Про первую строку `HTTP/1.1 200 Connection established` догадка близкая, но источник другой. Это ответ не GitHub, а твоего **прокси**, того самого `xray`. `curl` сначала просит прокси: «соедини меня с github.com», прокси отвечает «соединение установлено», и уже **через этот туннель** идёт настоящий запрос, на который отвечает GitHub (`HTTP/2 200` или `404`). Без VPN первой строки не было бы.
            
            **Прокси** (proxy): посредник между тобой и сайтом, запросы идут через него.
            
            **Заголовки** (headers): служебные строки ответа вида `имя: значение` после кода. Например, `server: github.com` (кто ответил) или `content-type: text/html` (что внутри).
