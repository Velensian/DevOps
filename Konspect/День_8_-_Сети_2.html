1. DNS - служба, которая по имени возвращает ip адрес необходимого сайта. Распределенная телефонная книга

    3. Резолвер(resolve - разрешить, найти) или же по другому DNS  сервер провайдера или роутера - это сервер который и ищет ip адрес нужного сайта из пункта b.
    4. Кэш и TTL - Доставать DNS адреса по такой цепочке долго и не удобно, поэтому ip адреса приходят с TTL(Time To Live), с временем хранения адреса в кэше, например 1 час, через час опять придется бегать по серверам и искать адрес.

    6. Файл /etc/hosts

      До всякого DNS система смотрит в локальный файл /etc/hosts. Там можно вручную прописать «имя → адрес». Именно там записано, что localhost это 127.0.0.1. Его используют для тестов: «пусть mysite.test ведёт на мой ноутбук».

      Почему это важно для DevOps

      Половина фраз «сайт не работает» на деле оказываются «не работает DNS»: запись не создана, указывает на старый сервер, не истёк кэш. Поэтому при диагностике первый вопрос: по имени не открывается, а по IP открывается? Если так, проблема в DNS.

        во втором случае HTTP1 - 200, значит удалось подключится к самому гизабу, а дальше HTTP2 - 404, следовательно страница не найдена на сайте гитхаба

        По факту: 

        Коды прочитаны верно: у твоего репозитория 200, у несуществующего пути 404. Сайт GitHub один и тот же, разница только в странице. Ровно то, что мы разбирали.

        Про первую строку HTTP/1.1 200 Connection established догадка близкая, но источник другой. Это ответ не GitHub, а твоего прокси, того самого xray. curl сначала просит прокси: «соедини меня с github.com», прокси отвечает «соединение установлено», и уже через этот туннель идёт настоящий запрос, на который отвечает GitHub (HTTP/2 200 или 404). Без VPN первой строки не было бы.

        Прокси (proxy): посредник между тобой и сайтом, запросы идут через него.

        Заголовки (headers): служебные строки ответа вида имя: значение после кода. Например, server: github.com (кто ответил) или content-type: text/html (что внутри).
